% ===================== 1. INTRODUCCIÓN =====================
\section{Introducción}
Detrás de todo compilador hay un análisis sintáctico que revisa que el código respete una estructura definida, y en Teoría de la Computación vimos que esa estructura se describe con gramáticas libres de contexto. Este proyecto fue la oportunidad de llevarlo a la práctica.

Creamos SmartRule, un lenguaje para escribir reglas de automatización del hogar inteligente, con una lógica simple de ``cuando pase esto, entonces haz esto otro'', más un ``si no'' opcional. Para este lenguaje diseñamos e implementamos un analizador sintáctico LL(1) descendente recursivo, con su gramática, conjuntos FIRST y FOLLOW, tabla predictiva, árbol sintáctico abstracto (AST) y mensajes de error claros, todo validado con 68 pruebas automatizadas.

\subsection{Antecedentes}
Todo compilador o intérprete se apoya en la teoría de autómatas y los lenguajes formales~\cite{brena}. Dentro de ese proceso, el análisis sintáctico (o \textit{parsing}) cumple un rol clave: revisar que la secuencia de tokens que entrega el analizador léxico respete la estructura gramatical del lenguaje.

Para describir esa estructura de manera formal se usan las Gramáticas Libres de Contexto (GLC), que sirven tanto para los lenguajes de programación como para los Lenguajes de Dominio Específico (\textit{Domain Specific Languages - DSL}), que están pensados para resolver problemas de un área en particular.

\subsection{Planteamiento del Problema}
Necesitábamos construir un analizador sintáctico para un lenguaje de dominio específico creado por nosotros. Este debía reconocer y validar los programas escritos en ese lenguaje, avisar cuando hubiera errores sintácticos con mensajes fáciles de entender, y representar la estructura de lo que se analiza mediante un Árbol Sintáctico Abstracto (AST).

\subsection{Objetivo General}
Diseñar e implementar un analizador sintáctico LL(1) descendente recursivo para el lenguaje de dominio específico \textit{SmartRule}. Para lograrlo, aplicamos Gramáticas Libres de Contexto, conjuntos \textit{FIRST} y \textit{FOLLOW} y análisis LL(1), además de construir el Árbol Sintáctico Abstracto (AST) y detectar los errores sintácticos del programa.

\subsection{Objetivos Específicos}
\begin{itemize}[leftmargin=1cm]
    \item Definir el dominio, propósito, tokens, palabras reservadas y sintaxis del lenguaje \textit{SmartRule}.
    \item Diseñar una Gramática Libre de Contexto (GLC) correcta, no ambigua, completa y coherente con el lenguaje propuesto.
    \item Analizar la gramática, identificando y corrigiendo recursividad, factorización y posibles ambigüedades.
    \item Calcular y justificar los conjuntos \textit{FIRST} y \textit{FOLLOW} para cada no-terminal.
    \item Construir la tabla predictiva LL(1), verificando la ausencia de conflictos.
    \item Implementar un analizador léxico (extendido a partir del cuaderno base entregado por el docente) y un analizador sintáctico LL(1) descendente recursivo desarrollado por el grupo.
    \item Construir un Árbol Sintáctico Abstracto (AST) que represente correctamente la estructura del programa.
    \item Implementar un mecanismo de detección y reporte de errores léxicos y sintácticos con mensajes claros y localizados.
    \item Desarrollar un conjunto de pruebas exhaustivo (\textgreater25 casos), incluyendo casos válidos, inválidos, casos límite y una extensión creativa integrada a la gramática.
    \item Documentar todo el proceso mediante un informe técnico en \LaTeX\ y un \texttt{README.md} reproducible.
\end{itemize}

% ===================== 2. DOMINIO DEL LENGUAJE =====================
\section{Dominio del Lenguaje: SmartRule}

\subsection{Descripción General}
\textit{SmartRule} es un Lenguaje de Dominio Específico (DSL) pensado para escribir reglas de automatización en sistemas de domótica e Internet de las Cosas (IoT). Su sintaxis sigue la lógica de la lengua natural: \textit{``SI ocurre una condición, ENTONCES ejecutar una o más acciones''}. Además, incluye una cláusula opcional \textit{SINO} (\texttt{ELSE}) para indicar qué hacer cuando la condición no se cumple.

\subsection{Justificación del Dominio}
Elegimos el hogar inteligente porque es un tema conocido y fácil de entender. Con este dominio pudimos mostrar de forma clara los conceptos vistos en el curso: reconocimiento de patrones, gramáticas, análisis predictivo LL(1), árboles sintácticos y manejo de errores. Además, es lo bastante simple como para mantener una gramática LL(1) válida, pero con la flexibilidad suficiente para agregar una extensión creativa.

\subsection{Alcance del Lenguaje}
El lenguaje \textit{SmartRule} permite:
\begin{itemize}[leftmargin=1cm]
    \item Definir múltiples reglas secuenciales en un mismo archivo.
    \item Evaluar condiciones compuestas mediante operadores lógicos \texttt{AND}, \texttt{OR} y \texttt{NOT}.
    \item Realizar comparaciones relacionales entre variables, sensores o valores numéricos.
    \item Ejecutar una o más acciones separadas por comas.
    \item Realizar asignaciones a actuadores o variables (\texttt{variable = valor}).
    \item Invocar acciones con o sin argumentos.
    \item Definir un bloque alternativo mediante la palabra reservada \texttt{ELSE}.
    \item Trabajar con valores booleanos \texttt{TRUE} y \texttt{FALSE}.
\end{itemize}

\subsection{Vocabulario Léxico: Palabras Reservadas y Tokens}

\subsection{Alfabeto del Lenguaje}
El alfabeto de \textit{SmartRule} es el conjunto finito de caracteres que acepta el analizador léxico:
\[
\Sigma = \Sigma_{L} \cup \Sigma_{D} \cup \Sigma_{S} \cup \Sigma_{W}
\]
donde:
\begin{itemize}[leftmargin=1cm]
    \item $\Sigma_{L} = \{\texttt{A},\dots,\texttt{Z},\ \texttt{a},\dots,\texttt{z},\ \texttt{\_}\}$: letras y guion bajo.
    \item $\Sigma_{D} = \{\texttt{0},\dots,\texttt{9}\}$: dígitos.
    \item $\Sigma_{S} = \{\texttt{\textgreater},\ \texttt{\textless},\ \texttt{=},\ \texttt{!},\ \texttt{,},\ \texttt{;}\}$: símbolos de operadores y separadores.
    \item $\Sigma_{W} = \{\text{espacio},\ \text{tabulación},\ \text{salto de línea},\ \text{retorno de carro}\}$: separadores ignorados.
\end{itemize}
El símbolo \texttt{!} solo es válido como parte de \texttt{!=}. Cualquier otro carácter (por ejemplo \texttt{\#} o \texttt{@}) produce un error léxico. Los lexemas se agrupan en las categorías de la Tabla~\ref{tab:tokens} y el analizador sintáctico trabaja con los \textit{terminales} \texttt{ID}, \texttt{NUM}, \texttt{OP\_REL}, \texttt{IGUAL}, \texttt{COMA}, \texttt{PUNTO\_COMA}, las palabras reservadas y el marcador de fin de entrada \texttt{\$}.

\subsection{Ejemplos de Programas}

\subsubsection{Ejemplos Válidos}
\begin{lstlisting}[style=grammartyle, caption={Ejemplos válidos en SmartRule}, label={lst:validos}]
WHEN temperatura > 28 AND humedad < 40 THEN encender ventilador;

WHEN luz == 0 OR movimiento == TRUE THEN encender luces, alarma = 1 ELSE apagar luces;

WHEN NOT puerta_abierta THEN activar_alarma;

WHEN nivel_agua >= 80 THEN bomba = 1, notificar_app;

WHEN presion < 10 AND NOT emergencia THEN abrir_valvula;
\end{lstlisting}

\subsubsection{Ejemplos Inválidos (Detectados por el Analizador)}
\begin{lstlisting}[style=grammartyle, caption={Ejemplos inválidos en SmartRule}, label={lst:invalidos}]
WHEN temperatura > THEN encender ventilador;        // Falta operando tras operador relacional
temperatura > 28 THEN encender luces;                // Falta palabra reservada WHEN
WHEN temperatura > 28 encender luces;                // Falta palabra reservada THEN
WHEN AND humedad < 40 THEN encender ventilador;      // Falta condición válida
WHEN temperatura > 28 THEN ;                         // Lista de acciones vacía
WHEN temperatura > 28 THEN accion1,, accion2;        // Coma extra
\end{lstlisting}


\subsection{Extensión Creativa}
En lugar de añadir elementos estéticos solo para cumplir con el requisito, decidimos implementar funcionalidades que realmente aportaran a la lógica de un sistema domótico y que se integraran de forma natural en la gramática. 

Por esto, incorporamos el operador \texttt{NOT} para negar variables (asignándole la mayor precedencia), añadimos el bloque \texttt{ELSE} para manejar el flujo alternativo cuando una condición no se cumple, y permitimos la ejecución de múltiples acciones simultáneas separadas por comas.

% ===================== 3. GRAMÁTICA LIBRE DE CONTEXTO =====================
\section{Gramática Libre de Contexto (GLC)}

\subsection{Definición Formal}
Se ha diseñado una Gramática Libre de Contexto $G = (V_N, V_T, P, S)$, donde:

\begin{itemize}[leftmargin=1cm]
    \item $V_N$ = \{Prog, Regla, ElsePart, Cond, OrExpr, OrTail, AndExpr, AndTail, NotExpr, RelExpr, RelExprTail, Factor, ListaAcciones, AccionTail, Accion, AsigOrCall, AsigTail\}
    \item $V_T$ = \{WHEN, THEN, ELSE, AND, OR, NOT, TRUE, FALSE, NUM, ID, OP\_REL, IGUAL, COMA, PUNTO\_COMA, \$\}
    \item $S = Prog$
    \item $P$ = Conjunto de producciones definido a continuación
\end{itemize}

\subsection{Producciones de la Gramática}
Las producciones se muestran agrupadas por no terminal; en la Tabla~\ref{tab:select} aparecen numeradas individualmente.
\begin{align*}
\mathit{Prog} &\to \mathit{Regla}\ \mathit{Prog} \mid \epsilon \\
\mathit{Regla} &\to \mathtt{WHEN}\ \mathit{Cond}\ \mathtt{THEN}\ \mathit{ListaAcciones}\ \mathit{ElsePart}\ \mathtt{PUNTO\_COMA} \\
\mathit{ElsePart} &\to \mathtt{ELSE}\ \mathit{ListaAcciones} \mid \epsilon \\
\mathit{Cond} &\to \mathit{OrExpr} \\
\mathit{OrExpr} &\to \mathit{AndExpr}\ \mathit{OrTail} \\
\mathit{OrTail} &\to \mathtt{OR}\ \mathit{AndExpr}\ \mathit{OrTail} \mid \epsilon \\
\mathit{AndExpr} &\to \mathit{NotExpr}\ \mathit{AndTail} \\
\mathit{AndTail} &\to \mathtt{AND}\ \mathit{NotExpr}\ \mathit{AndTail} \mid \epsilon \\
\mathit{NotExpr} &\to \mathtt{NOT}\ \mathit{NotExpr} \mid \mathit{RelExpr} \\
\mathit{RelExpr} &\to \mathit{Factor}\ \mathit{RelExprTail} \\
\mathit{RelExprTail} &\to \mathtt{OP\_REL}\ \mathit{Factor} \mid \epsilon \\
\mathit{Factor} &\to \mathtt{NUM} \mid \mathtt{ID} \mid \mathtt{TRUE} \mid \mathtt{FALSE} \\
\mathit{ListaAcciones} &\to \mathit{Accion}\ \mathit{AccionTail} \\
\mathit{AccionTail} &\to \mathtt{COMA}\ \mathit{Accion}\ \mathit{AccionTail} \mid \epsilon \\
\mathit{Accion} &\to \mathtt{ID}\ \mathit{AsigOrCall} \\
\mathit{AsigOrCall} &\to \mathtt{IGUAL}\ \mathit{Factor} \mid \mathtt{ID}\ \mathit{AsigTail} \mid \mathtt{NUM} \mid \mathtt{TRUE} \mid \mathtt{FALSE} \mid \epsilon \\
\mathit{AsigTail} &\to \mathtt{IGUAL}\ \mathit{Factor} \mid \epsilon
\end{align*}

\subsection{Análisis y Transformaciones de la Gramática}

\subsubsection{Recursión Izquierda}
Tras el análisis de las producciones, verificamos que la gramática \textbf{no presenta recursión izquierda}, ni directa ni indirecta (verificado por inspección de las producciones: ningún no terminal puede derivar una forma sentencial que comience con él mismo). Para el caso de listas (reglas, acciones, operadores lógicos), se empleó \textbf{recursión por la derecha} mediante las reglas \textit{Tail} (\texttt{OrTail}, \texttt{AndTail}, \texttt{AccionTail}), lo cual es idóneo para un parser LL(1) descendente recursivo.

\subsubsection{Factorización por la Izquierda}
Durante el análisis se detectó un \textbf{conflicto FIRST/FIRST} en la producción de acciones. La versión inicial de la gramática era:
\begin{align*}
\mathit{Accion} &\to \mathit{ID}\ \mathit{AsigOrCall} \mid \mathit{ID}\ \mathit{ID}\ \mathit{IGUAL}\ \mathit{Factor}\\
\mathit{AsigOrCall} &\to \mathit{IGUAL}\ \mathit{Factor} \mid \mathit{Factor} \mid \epsilon
\end{align*}
Las dos alternativas de \textit{Accion} comienzan con \texttt{ID}, por lo que con un solo token de anticipación el parser no puede elegir entre ellas. Además, \textit{AsigOrCall $\to$ Factor} también puede derivar \texttt{ID}, de modo que una entrada como \texttt{encender luces} admitía más de una derivación. Por lo tanto esa versión \textbf{no era LL(1)}.

Se resolvió \textbf{factorizando por la izquierda} el prefijo común \texttt{ID} y extrayendo la parte opcional de la asignación en un nuevo no terminal, \textit{AsigTail}:
\begin{align*}
\mathit{Accion} &\to \mathtt{ID}\ \mathit{AsigOrCall}\\
\mathit{AsigOrCall} &\to \mathtt{IGUAL}\ \mathit{Factor} \mid \mathtt{ID}\ \mathit{AsigTail} \mid \mathtt{NUM} \mid \mathtt{TRUE} \mid \mathtt{FALSE} \mid \epsilon\\
\mathit{AsigTail} &\to \mathtt{IGUAL}\ \mathit{Factor} \mid \epsilon
\end{align*}
El lenguaje generado no cambia; las cuatro formas de acción siguen siendo válidas:
\begin{itemize}[leftmargin=1cm]
    \item Asignación directa, \texttt{bomba = 1}: \textit{AsigOrCall $\to$ IGUAL Factor}.
    \item Llamada sin argumento, \texttt{activar\_alarma}: \textit{AsigOrCall $\to \epsilon$}.
    \item Llamada con argumento, \texttt{encender luces} o \texttt{alarma 5}: \textit{AsigOrCall $\to$ ID AsigTail} con \textit{AsigTail $\to \epsilon$}, o \textit{AsigOrCall $\to$ NUM}.
    \item Asignación con objeto, \texttt{encender luces = 100}: \textit{AsigOrCall $\to$ ID AsigTail} con \textit{AsigTail $\to$ IGUAL Factor}.
\end{itemize}

\subsubsection{Ambigüedad y Precedencia}
La gramática es \textbf{no ambigua}: toda gramática LL(1) lo es, y en la Sección~\ref{sec:ll1} se demuestra que ésta cumple la condición LL(1). La precedencia de operadores se garantiza mediante la jerarquía de no terminales:
\[
NOT > AND > OR
\]
Las comparaciones relacionales (\texttt{OP\_REL}) se evalúan entre dos factores y no son encadenables, tal como se define en \textit{RelExpr} (el caso \texttt{I8} de la Tabla~\ref{tab:casos} lo comprueba).

\subsection{Conjuntos FOLLOW}
El conjunto \textit{FOLLOW}(A) contiene todos los terminales que pueden aparecer inmediatamente después del no-terminal $A$ en alguna derivación sentencial. Algunos casos que conviene justificar:
\begin{itemize}[leftmargin=1cm]
    \item $\texttt{AND} \in FOLLOW(NotExpr)$, $FOLLOW(RelExpr)$ y $FOLLOW(RelExprTail)$, porque en $AndExpr \to NotExpr\ AndTail$ lo que sigue a \textit{NotExpr} es \textit{AndTail}, cuyo FIRST contiene \texttt{AND}.
    \item $FOLLOW(Factor)$ reúne \texttt{OP\_REL} (por \textit{RelExprTail}), los seguidores de \textit{RelExpr} (\texttt{AND}, \texttt{OR}, \texttt{THEN}) y los seguidores de \textit{AsigOrCall} y \textit{AsigTail} (\texttt{COMA}, \texttt{ELSE}, \texttt{PUNTO\_COMA}), porque \textit{Factor} puede ser el último símbolo de esas producciones.
    \item $FOLLOW(ElsePart) = \{\texttt{PUNTO\_COMA}\}$, ya que \textit{ElsePart} cierra la regla justo antes de \texttt{;}.
\end{itemize}

\subsection{Analizador Léxico}
El analizador léxico fue tomado como base del cuaderno \texttt{anlizador\_lexico1.ipynb} provisto por el docente, y posteriormente \textbf{extendido} para dar soporte a los requerimientos del lenguaje \textit{SmartRule}.

\textbf{Características implementadas:}
\begin{itemize}[leftmargin=1cm]
    \item Implementación mediante \texttt{re.finditer} con patrones nombrados~\cite[sección \textit{Writing a Tokenizer}]{pythonre}.
   
    \item Reconocimiento de operadores relacionales compuestos (\texttt{>=}, \texttt{<=}, \texttt{==}, \texttt{!=}).
    \item Soporte para \texttt{=} (\texttt{IGUAL}) y \texttt{,} (\texttt{COMA}).
    \item Clasificación automática de palabras reservadas (\texttt{WHEN}, \texttt{THEN}, \texttt{ELSE}, \texttt{AND}, \texttt{OR}, \texttt{NOT}, \texttt{TRUE}, \texttt{FALSE}); no distinguen mayúsculas de minúsculas (\texttt{when} equivale a \texttt{WHEN}).
    \item Ignorado de espacios, tabulaciones y saltos de línea.
    \item Detección de símbolos no reconocidos con excepción \texttt{LexerError}.
    \item Adición automática del token \texttt{EOF} (\$) para facilitar el análisis sintáctico.
\end{itemize}


\newpage

\subsection{Analizador Sintáctico LL(1) Descendente Recursivo}
Implementamos el analizador sintáctico completamente desde cero. Aunque existía la opción de usar generadores automáticos como ANTLR o Yacc, preferimos programarlo a mano para cumplir con la rúbrica y entender realmente el funcionamiento interno del análisis predictivo. 

En la arquitectura del código, creamos un método \texttt{parse\_*()} para cada no-terminal de la gramática, configurando el parser para que decida su camino leyendo un solo token de anticipación, sin usar \textit{backtracking}. Esta estructura nos permitió manejar de forma limpia la recursión por la derecha, el bloque \texttt{ELSE} y los distintos tipos de asignaciones.

\subsection{Manejo de Errores}
Diseñamos el sistema de errores con la idea de que los mensajes guíen la corrección del código, en lugar de solo lanzar una excepción genérica que detenga el programa. Esto resultó ser muy útil durante nuestra propia fase de depuración. 

\vspace{0.5cm}

Si se ingresa un carácter inválido, el analizador léxico (\texttt{LexerError}) indica la línea y columna exacta del problema. Por el lado sintáctico, el \texttt{ParserError} detalla qué token se esperaba y cuál se encontró en esa posición. Además, agregamos una opción (\texttt{-e}) para que el analizador no se detenga en el primer error y reporte todos los fallos encontrados en una sola pasada.

% ===================== 7. CONCLUSIONES Y RECOMENDACIONES =====================
\section{Conclusiones}

Al terminar el proyecto, podemos decir que logramos lo que nos propusimos: diseñar e implementar un analizador sintáctico LL(1) descendente recursivo que funciona para \textit{SmartRule}. Más allá del resultado, el proceso nos sirvió para entender de verdad cómo se conectan la teoría y la práctica.

\begin{itemize}[leftmargin=1cm]
    \item \textbf{Una gramática que cumple lo que prometía:} La GLC que diseñamos no es ambigua, respeta la precedencia de los operadores y es LL(1). En el camino encontramos un conflicto FIRST/FIRST en las acciones, que resolvimos factorizando por la izquierda. Fue una buena experiencia, porque vimos en un caso real por qué importan estas condiciones.
    \item \textbf{Análisis formal completo:} Calculamos y justificamos los conjuntos \textit{FIRST} y \textit{FOLLOW} y con ellos armamos la tabla LL(1), que quedó sin conflictos.
    \item \textbf{Implementación propia:} Programamos el parser desde cero, sin generadores automáticos, y extendimos el analizador léxico a partir del cuaderno base que entregó el profesor.
    \item \textbf{Árbol y errores claros:} El AST muestra de forma ordenada la estructura de cada regla, y el sistema reporta los errores léxicos y sintácticos indicando qué se esperaba, qué se encontró y dónde, lo que ayuda bastante a corregirlos.
    \item \textbf{Pruebas y orden del código:} Las 68 pruebas automatizadas, que incluyen los 25 casos documentados (10 válidos, 10 inválidos y 5 límite), pasaron correctamente. Además, organizamos el código con una arquitectura modular y dejamos documentación (\texttt{README.md}, gramática formal, este informe en \LaTeX\ y ejemplos) para que cualquiera pueda reproducir el trabajo.
\end{itemize}

Este proyecto nos permitió aplicar los contenidos del curso en algo concreto y nos dejó una base sólida para seguir mejorando el lenguaje en el futuro.

\section{Recomendaciones y Trabajo Futuro}

Como trabajo futuro para seguir mejorando el lenguaje, consideramos que el siguiente paso lógico sería incorporar soporte para paréntesis, lo que permitiría agrupar condiciones complejas con mayor libertad. También sería útil sumar una etapa de análisis semántico para validar la existencia de variables y comprobar los tipos de datos antes de evaluar la regla. 

A más largo plazo, nos gustaría traducir estas reglas a código ejecutable dentro de un simulador IoT, además de desarrollar una interfaz gráfica para visualizar el árbol sintáctico directamente, sin depender de exportar archivos a \texttt{graphviz}.

\subsection{Anexo C: Gramática Completa en Formato BNF}
\begin{lstlisting}[style=grammartyle, caption={Gramática BNF completa de SmartRule}]
<Prog>           ::= <Regla> <Prog> | ε
<Regla>          ::= WHEN <Cond> THEN <ListaAcciones> <ElsePart> PUNTO_COMA
<ElsePart>       ::= ELSE <ListaAcciones> | ε
<Cond>           ::= <OrExpr>
<OrExpr>         ::= <AndExpr> <OrTail>
<OrTail>         ::= OR <AndExpr> <OrTail> | ε
<AndExpr>        ::= <NotExpr> <AndTail>
<AndTail>        ::= AND <NotExpr> <AndTail> | ε
<NotExpr>        ::= NOT <NotExpr> | <RelExpr>
<RelExpr>        ::= <Factor> <RelExprTail>
<RelExprTail>    ::= OP_REL <Factor> | ε
<Factor>         ::= NUM | ID | TRUE | FALSE
<ListaAcciones>  ::= <Accion> <AccionTail>
<AccionTail>     ::= COMA <Accion> <AccionTail> | ε
<Accion>         ::= ID <AsigOrCall>
<AsigOrCall>     ::= IGUAL <Factor> | ID <AsigTail> | NUM | TRUE | FALSE | ε
<AsigTail>       ::= IGUAL <Factor> | ε
\end{lstlisting}

\subsubsection{Cadena derivada}
La forma sentencial final es la secuencia de terminales
\begin{center}
\texttt{WHEN ID OP\_REL NUM AND ID OP\_REL NUM THEN ID ID PUNTO\_COMA}
\end{center}
que corresponde, en el mismo orden, a los lexemas
\begin{center}
\texttt{WHEN temperatura \textgreater{} 28 AND humedad \textless{} 40 THEN encender ventilador ;}
\end{center}
Por consiguiente, se demuestra que la sentencia pertenece al lenguaje generado por la gramática $G_{SmartRule}$ mediante derivación por la izquierda.
